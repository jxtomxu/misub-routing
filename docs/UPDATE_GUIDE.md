# 更新与回滚

## 规则内容自动同步

`sync-rules.yml` 每天 20:17 UTC（北京时间次日 04:17）检查 22 个公开上游，也支持 Actions 页手动运行。同步时检查 HTTP、文件大小与规则数量；全部下载成功后才替换缓存并构建。未知类型、空内容、数量异常或测试失败时不提交更新。只有注释或时间戳变化时保留原缓存，不产生空提交。

`build.yml` 在 Schema、生成器、脚本、测试或工作流变更时构建，也可手动运行。它验证 Schema、组与引用、目标文件、21 个示例的离线匹配及敏感信息签名；成功才提交新的 dist。两个工作流共享串行队列，避免互相覆盖。推送碰到主分支并发改动时会失败，不强推；重新运行即可。

客户端需要分别开启规则资源更新；MiSub 的节点订阅有自己的更新间隔，和 GitHub 规则同步独立。两端都依赖网络可用。GitHub 可能因长期无仓库活动而停用定时工作流，需在 Actions 页面重新启用；不能承诺平台永久免维护。

## 修改规则

1. 修改 `schema/routing.yaml`，保留八组，使用唯一 ID 和优先级。新增上游需填写完整元数据和缓存，再验证目标格式及许可证。
2. 本地安装 `python3 -m pip install -r requirements.txt`。
3. 运行 `./scripts/build` 和 `./scripts/validate`；检查 `dist/BUILD_REPORT.json` 中未支持规则与来源。
4. 提交 Schema、必要缓存、生成器和对应 dist；或推送后观察 Build 工作流。
5. 现有上游内容变化会通过既有规则集地址自动下发。若增加/删除来源、调整规则顺序、组结构、DNS 或客户端模板，Quantumult X 和 Shadowrocket 的本地配置不一定会自动合并结构变化，需对照新版模板更新；Mihomo 的远程配置也取决于本机覆写行为。不要把此类更改说成已自动生效。

## 回滚

在 GitHub 查看历史，选择已验证的提交，通过 revert 恢复 Schema、缓存和 dist 的一致版本；也可暂时将客户端 URL 指向已验证 commit 的 raw 地址。回滚后检查规则资源的更新时间和实际命中；固定到 commit 后将不再跟随最新版本，需要改回 `main` 才恢复自动更新。
